## What SceneCaster is
An Electron desktop app (Mac + Windows) by e-llusion media for running theatrical shows. Dual-display: operator UI on a laptop/monitor, fullscreen video output on an LED wall/projector. Two-key operation — **B** advances the backdrop video, **L** advances lighting cues independently. Sold as full shows ($899) or (soon) à la carte scenes ($125). Shows live now: Shrek (Adult + Jr), Frozen (Adult + Jr), Matilda (Adult + Jr), Little Mermaid (Adult + Jr), Moana (Jr), Annie (Adult + Jr — see storefront-gate note), Into the Woods (Adult + Jr) — live & purchasable 2026-09-13, Come From Away (Adult — backend live, storefront pending).

### Payment flow (end to end)
**Stripe → Supabase → buyer → SceneCaster app → Render → Cloudflare R2**
1. Buyer clicks Buy on the Lovable store → Supabase edge function `create-checkout-session` builds a Stripe Checkout session.
2. Payment succeeds → Stripe fires `checkout.session.completed` → Supabase edge function `payments-webhook` **mints the JWT license key + emails it** (with the app download link, now via GitHub's `/latest/` alias).
3. Buyer downloads SceneCaster, installs, enters the key.
4. App validates the key, shows a closing-date picker, POSTs `{token, closingDate}` to Render `/activate`, gets the final activated token.
5. App fetches cues + manifest from Render. For each scene file, the app POSTs `{token, sceneKey}` to Render's `/download-url`, which verifies the license owns that scene and mints a short-lived signed R2 URL; the app then downloads directly from that URL.

### Backend endpoints
- **Render:** `POST /activate`, `GET /cues/:showId`, `GET /manifest`, `POST /download-url` (added 2026-07-17 — license-gated signed R2 URL, 6h expiry), `GET /health`, `GET /browse` + `/browse/auth` + `/browse/api/*` (added 2026-10-06 — password-protected R2 file browser). (Old `POST /webhook/payhip` is dead.)
- **Supabase edge functions:** `create-checkout-session`, `payments-webhook` (mint + email).

### Licensing
- **JWT signed with ES256 (asymmetric EC key pair), not a shared secret.** Migrated 2026-07-10 from the original HS256 scheme, which signed and verified with the *same* secret — and that secret was embedded in plaintext inside the shipped app, meaning anyone who extracted it could forge a valid license. Now: a private key lives **only** in Render's `LICENSE_PRIVATE_KEY` env var (never shipped anywhere), and both the app and Render verify using the public half only, which is safe to embed since it can't be used to create new licenses. Supabase's `payments-webhook` mints the very first (purchase) token and must sign with the same private key.
- **No HS256 fallback exists anymore.** The migration confirmed zero outstanding HS256-signed licenses before cutover, so the old verification path was removed outright rather than kept as a transitional dual-accept state. Any token that isn't ES256-signed is now flatly rejected everywhere (app, Render `/activate`).
- **NOT actually machine-bound, despite the field existing.** `checkLicense()` in `main.js` checks a `payload.mid` field, but nothing anywhere (not the app, not the `/activate` endpoint) ever sets or sends a machine ID — so the check is silently skipped every time. In practice, any license key can be activated on unlimited computers today. Confirmed 2026-07-06; Mark is leaning toward leaving this as-is but hasn't made a final call — don't "fix" this without checking with him first (see Claude auto-memory `project_scenecaster_license_multimachine.md`).
- Hard expiry (this part IS enforced).
- Token fields: `p` (packID — a string for a full show/single scene, or an **array** of scene identifiers for a multi-scene à la carte purchase), `e` (expiry), `pd` (purchase date — only on the initial token, drives the date picker).
- Two-phase activation: purchase token → customer picks closing date → `/activate` caps at purchase + 12 months → clean final token. `/activate` is completely stateless — no tracking of already-used purchase tokens, so the same purchase key can be re-activated freely (useful for re-testing).
- **Ownership/entitlement checks are show-scoped, not just name-matched (added 2026-07-13).** `isOwned()` in `renderer/app.js` and the show-resolution logic in `main.js`'s `load-bundled-show` now verify a purchased scene actually belongs to the specific show being loaded — not just that its name appears somewhere in the license. Defense-in-depth against a future naming collision leaking access to another show's scene; see the naming-rule section below for the collision problem itself.

### 🔵 Known issues / backlog
- **✅ FIXED 2026-07-14 — LED/external display infinite-refresh-loop regression, shipped as `v1.0.2`.** Was a critical regression: `display-added` fires correctly on projector connection (detection itself was fine), but `display-metrics-changed` scheduled an LED window refresh on every event fire, and that refresh itself altered display metrics (repositioning/resizing the LED window), which re-triggered `display-metrics-changed` — a self-sustaining feedback loop. Logged 288 loop iterations at ~500ms each (~144s of continuous teardown/rebuild) in James's original test; the manual "Open External Screen" fallback was also broken by it (window destroyed roughly every 500ms, faster than a click could take effect).
  **Root cause:** the `display-metrics-changed` listener added in commit `37be70a` couldn't distinguish a genuine external metrics change from a metrics change the app's own refresh just caused.
  **Fix (diff approach):** added `getDisplaySignature()` to `main.js` — before scheduling a refresh from `display-metrics-changed`, compares new display bounds/resolution against the last known signature; only refreshes if something genuinely differs. Preserves the original fix's intent (catching real external metrics changes on an already-connected display) while breaking the self-feedback loop.
  **Underlying LED-window-dropping fixes it builds on (still in this build):** two earlier candidate fixes committed 2026-07-13/14 — display-event handling (commit `37be70a`: settle-delay on startup, `display-metrics-changed` listener added, all triggers debounced through one shared timer) and renderer-health monitoring (commit `1c617ee`: auto-recreates the LED window on `unresponsive`/`render-process-gone`, logged with a distinct `[renderer-health]` prefix). Both remain in `v1.0.2` alongside the new diff-check fix.

- **⚠️ CORRECTION to earlier 2026-07-14 entry — the OS 26.5.2 update did NOT fix the notarytool SIGBUS bug.** Re-confirmed via multiple later crash logs the same day (`notarytool-2026-07-14-133823.ips`, `-142815.ips`, `-145957.ips`, and others) — every one shows an identical `recursionInfoArray` (depth 502, keyFrame `EventLoopFuture.map<A>`) to the original diagnosis, same bug, unchanged, post-update. **Note for future readers:** this `recursionInfoArray` field lives on a *different, non-faulting* thread than the one that actually triggers `EXC_BAD_ACCESS`/`SIGBUS` — a naive check of only `threads[faultingThread]` will show a shallow ~104-frame stack and *miss it entirely* (this happened once during today's session — don't repeat that mistake; deep-search every thread in the `.ips` JSON for the `recursionInfoArray` key). This morning's single clean pass was luck, not a fix.
  **Confirmed root cause (still accurate):** `EXC_BAD_ACCESS`/`SIGBUS`, "Could not determine thread index for stack guard region", inside nested `EventLoopFuture.map`/`flatMap` closures under `S3ChunkedStreamReader.streamChunks` → `AWSSigner.chunkStringToSign`. Apple's own notarytool (1.0.0 build 28) recursively chains a closure per upload chunk instead of looping flatly, blowing a background NIO worker thread's stack. **Confirmed via an Apple Developer Forums thread that other users hit the identical signature** — this is a real, externally-documented Apple bug, not something specific to this machine, this zip, or this network.
  **The bug is genuinely non-deterministic.** Repeated attempts on the identical file, identical machine, identical network conditions produced wildly different outcomes in a single session: instant crash, crash at 3%, 9%, 18%, 30%, 48% (twice, same exact byte count both times — 79.9MB), a silent hang, and eventually clean 100% uploads.
  **Ruled out as causes:** network congestion/bandwidth (tested directly — crashed repeatedly on a clear network, close to router, no competing traffic), file type (crashed identically on both `.zip` and `.dmg`), Claude Code sandbox (crashes identically in bare Terminal with zero Claude Code involvement).
  **Possible contributing factor, unconfirmed — do not treat as settled:** submissions may be more likely to crash under concurrent high-bandwidth network usage (e.g. simultaneous gaming). One anecdotal data point observed 2026-07-14 (a crash while gaming was reportedly active, a clean pass immediately after being asked to pause) — not reproducible on a direct retest under controlled conditions, and not tested rigorously. Worth testing further, but not a confirmed root cause or fix.
  **Only real "fix": brute-force retry.** No configuration change reliably prevents it. Budget for multiple failed attempts when notarizing (2026-07-14: 8+ failures before a clean pass on one build alone). `caffeinate -i` prevents sleep-related interruptions but does not prevent this specific crash.
  **A crash doesn't necessarily mean the submission is lost, but it doesn't necessarily mean it's fine either.** The crash only kills the local `notarytool` process — poll the submission ID with `xcrun notarytool info <id> ...` before assuming it's gone. But some submissions crash mid-upload (confirmed via crash log: faulting stack still inside `S3ChunkedStreamReader.streamChunks`, no upload-complete confirmation ever printed) and the truncated upload can leave Apple's side waiting on data that will never arrive — one 2026-07-14 submission sat at `In Progress` for 53+ minutes with zero movement this way. ## "Director's Custom Mode" — ✅ BUILT, MERGED TO MAIN, LIVE in the public `v1.0.1` release (2026-07-13)
Lets directors/producers customize their show without touching e-llusion's master content. **Standard, free feature — not a paid tier** (decided 2026-07-03). Fully built, merged from branch `custom-mode-foundation` into `main` on 2026-07-05 (25 commits), plus 4 more polish commits on 2026-07-06 (see below). A properly **notarized** test build was sent to James on 2026-07-06 for double-checking (the 2026-07-05 build he'd been sent was unsigned and hit a Gatekeeper "Apple could not verify" block — unrelated to app functionality, just needed real notarization). As of the `v1.0.1` release (2026-07-13), this is no longer just a test build — it's what customers actually download from GitHub Releases.

**Features, all live:**
1. **Upload** your own video or still as a new scene (videos always loop; stills hold until B).
2. **Skip** a scene — grays out, struck-through, stays in the list, won't play.
3. **Reorder** — drag-and-drop any row, cross-act allowed; **auto-scrolls the queue** when dragging a row near the top/bottom edge (added 2026-07-06).
4. **Reset** — two variants: **Restart Run** (playback position only, safe mid-show) and **Reset to Original** (wipes all customizations back to master).
5. **Duplicate** any scene — fully independent copy (own color/cues/position/dissolve); auto-numbered "(Copy 1)", "(Copy 2)" etc., continuing off the original name even when copying a copy.
6. **Delete** — e-llusion's own scenes just leave the running order (Reset brings them back); the customer's own added/duplicated scenes are removed for good.
7. **Rename** — uploaded/duplicated scenes only; e-llusion's original scene names stay read-only.
8. **Per-scene dissolve length override** — set via each scene's **⋯ → Set Dissolve In…** menu (0–3s); governs the transition INTO that scene specifically. Transition *type* stays fixed globally — only length is per-scene. Clear it via the same menu (**⋯ → Use default dissolve**, shown only when an override is set) — no need for Undo or a full Reset.
9. **Printable PDF cue sheet** — reflects the live customized order (sequential numbering, skipped rows struck through, blackouts/renames/uploads flagged, per-scene transition length, MTI pages, trigger notes, lighting cues).
10. **Undo / Redo** — Cmd+Z / Cmd+Shift+Z, full history stack.

## Cloudflare R2 Migration — ✅ FULLY LIVE 2026-07-17

### Why
A concrete production incident (2026-07-16, see Known Issues) exposed a real, scale-relevant risk: Google Drive enforces a **per-file download quota**, shared across every customer downloading that show. Two Frozen scene files hit it mid-download during ordinary stress testing; Drive silently served a ~2KB HTML "too many downloads" error page with an HTTP 200 status, which the app wrote to disk as a corrupt `.mp4`. Mark's decision: migrate to **Cloudflare R2**, with **license-gated signed URLs as a core requirement, not a bolt-on** — access control needed to move with the storage, not be added after.

### Architecture
- App has an activated license (unchanged).
- For each scene file, the app POSTs `{token, sceneKey}` to Render's new `POST /download-url`.
- Backend verifies the JWT, checks expiry (a real gap found while building this — `verifyJWT`'s `opts.ignoreExpiry` parameter was accepted but never actually read anywhere; added a proper `isExpired()` check in `lib/license.js`), and checks ownership via `lib/ownership.js`'s `isSceneOwned()` — a server-side mirror of the app's `isOwned()` (`renderer/app.js:514`), deliberately **stricter**: it re-checks `manifest.packs[id].includes(sceneKey)` even for full-show grants, since the server has no cues-file context to lean on the way the app does.
- On success, mints a **6-hour presigned R2 GET URL** via `lib/r2.js`'s `S3Client` (R2 is fully S3-API-compatible; `region: 'auto'`, endpoint from `R2_S3_ENDPOINT`). 6h covers one real download session — unrelated to the license's own 12-month expiry; a later re-download just mints a fresh URL.
- App downloads directly from that signed URL. The existing download validation (≥1MB floor, content-length match, delete-partial-on-failure, never count a bad download as successful — originally built for the Drive quota incident) carries over unchanged and still protects against any truncated/corrupt download, regardless of source.
- `manifest.json`'s `files` entries: `fileId` (Drive) replaced with `r2Key` (R2 object key, by convention identical to the show-prefixed filename).

### Backend files added
- `lib/r2.js` — R2 `S3Client` singleton, `maxAttempts: 8` (see network section below for why).
- `lib/license.js` — `isExpired(payload)`.
- `lib/ownership.js` — `isSceneOwned(payload, sceneKey, manifest)`.
- `scripts/migrate-to-r2.js` — bulk migration script (see below). Its local-source-resolution and upload-with-retry logic is exported (guarded behind `require.main === module`) for reuse by other scripts.
- `scripts/reupload-scene.js` — added 2026-07-19. Force re-uploads one already-migrated scene's local source to its existing `r2Key`, for the case where a scene gets re-edited after delivery. Never touches `manifest.json`. Hard-stops if the local file's size exactly matches what's already in R2 (accidental-rerun guard, overridable with `--force`); verifies via `HeadObjectCommand` before/after that size and ETag actually changed. Usage: `node scripts/reupload-scene.js <sceneKey> [--force]`.
- `server.js` — new `POST /download-url` route; caches `manifestData` in memory at boot (right after `validateManifest()` passes) rather than re-reading the file per request. Also mounts the browse router at `/browse` (added 2026-10-06).
- `lib/browse.js` — added 2026-10-06. Express router for the R2 File Browser: password auth (HMAC-signed cookie, 24h expiry, `BROWSE_PASSWORD` env var), R2 listing endpoints (`/api/shows`, `/api/scenes`, `/api/files`), presigned download URLs (`/api/download`), and still-image thumbnail proxy (`/api/thumbnail`). Reads `manifest.json` at load time to check whether a scene has a clean video available (links to the existing flat key, not a duplicate).
- `browse/index.html` — added 2026-10-06. SPA for the R2 File Browser: login, show grid, scene list, file detail views with color-coded badges (YT red, FB blue, STILL green, CLEAN orange), still-image preview, one-click download via presigned URLs. Dark theme (#0f0f17 bg, #FF5A0D orange accent), mobile-friendly.
- `scripts/upload-media.js` — added 2026-10-06. Bulk upload of YT/FB/stills from `06_FINALS` to R2 under `media/{show-slug}/{scene}/` prefix. Usage: `node scripts/upload-media.js <show-slug> <finals-dir>`. Resumable (skips already-uploaded files via HeadObject), 3 retries per file, verifies size after upload. Used to populate Come From Away (165 files, ~10 GB, 0 failures).

### App files changed
- `main.js`'s `download-file` IPC handler: now two-step (read `LICENSE_FILE` directly — no renderer round-trip for the token — POST to `/download-url`, then download from the returned signed URL).
- `renderer/app.js`'s `checkAndDownload()`: `neededMap` now carries `sceneKey` (the manifest key itself) alongside `filename`, since that's what `/download-url` needs.
- `isOwned()` itself needed no changes — it never touched `fileId`/`r2Key`.

### The bulk migration saga (2026-07-17)
**First attempt — Drive quota, badly.** The migration script initially pulled all 93 scene files from Google Drive (fileId → download → upload to R2). Drive's quota tripped almost immediately — 92 of 93 files failed within about a minute of starting. Confirmed this is a real, aggressive limit, not a fluke.

**Pivot — the files already existed locally.** Rather than fight Drive's quota, checked whether the source video files existed on Mark's own external drives — they did, entirely. `EM_Scenes` (Frozen + Matilda, in each show's `_Finals` folder) and `Jeunet` (Shrek, in `em15256_Shrek/Final Movies/Final no WM/`) together covered all 93 files. Rewrote `migrate-to-r2.js` to check local paths first (trying both the exact manifest filename and a prefix-stripped variant — two different naming exceptions were found, `Matilda_Bedroom.mp4` keeps its full prefix on disk while its siblings don't, and `Shrek_Swamp_Wedding` is the reverse) and only fall back to Drive if no local file exists. A `--dry-run` flag was added to confirm resolution before ever touching real data — used repeatedly to verify all 93 files matched before each real run.

**Second bug — TLS instability, independent of Drive.** Even sourcing locally, R2 *uploads* started failing with `SSL routines:ssl3_read_bytes:...alert bad record mac` — not a Drive problem at all, this was the machine's own Wi-Fi network under sustained large-file transfer. Mitigated (not fully fixed) by switching the upload to `@aws-sdk/lib-storage`'s `Upload` (chunked, `queueSize: 1` to serialize parts instead of 4-way concurrent) plus an application-level retry loop (4 attempts, fresh connection each time) and bumping the S3 client's own `maxAttempts` to 8. This got most files through but still left a real, non-trivial failure rate (a full pass once ended 63/93 done, 30 failed even after 4 retries each) — Wi-Fi remained inherently unreliable for this volume of sustained transfer.

**Actual fix — wired Ethernet.** Once Mark connected via a USB-Ethernet adapter (confirmed via `route get default` → `en6`, hardware port `AX88179B`, not `en0`/Wi-Fi), every remaining file uploaded cleanly on the first attempt, zero retries. All 93 files migrated and verified (`HeadObjectCommand` confirms each object exists in R2 at ≥1MB, matching `validate-manifest.js`'s own size floor) — confirmed via an exhaustive cross-check that R2's bucket contents match `manifest.json`'s `r2Key`s 1:1, no missing, no orphaned, no undersized objects.

**Resumability design (worked exactly as intended throughout):** the script writes `manifest.json` back to disk immediately after each successful file, not batched — so every interruption (Drive quota, TLS failures, deliberately pausing to investigate) left the manifest in a valid, safely-resumable state. Re-running always picked up exactly where it left off.

## Show configuration & adding a new show
Every show is **data on the backend**, not baked into the app (the "empty player" design). Three pieces per show:

1. **Cues file — ONE PER SHOW variant.** `cues/[showId].json` (e.g. `shrek-adult.json`, `frozen-jr.json`) — the scene list, backdrop triggers, and lighting cues. Lives in the **`showrunner-backend` GitHub repo**, served by Render at `GET /cues/:showId`. The app caches it locally at `~/.scenecaster/cues-[showId].json`.
2. **Manifest — ONE SHARED file for ALL shows.** A single `manifest.json` in the backend repo, served at `GET /manifest`. Each show is a **"pack"** inside it, listing that show's video filenames + their R2 object keys (`r2Key` — as of 2026-07-17; was Drive `fileId` before the R2 migration). Adding a show = add a new pack section, NOT a new manifest file.
3. **Video files → Cloudflare R2** (as of 2026-07-17, was Google Drive before). The actual .mp4s live in the `scenecaster-videos` R2 bucket; the manifest holds their R2 object keys (by convention, identical to the show-prefixed filename, e.g. `Frozen_Elsa_Bedroom.mp4`) so Render's `/download-url` can mint a signed URL for the app to download from. **Moana is the one exception** — it's being built directly against R2 from the start, never had Drive entries.

**To add a new show (no app rebuild needed):**
1. Upload the show's videos directly to the `scenecaster-videos` R2 bucket (via `rclone`, the AWS CLI configured for R2, or the Cloudflare dashboard) — object key = the show-prefixed filename, matching the hard naming rule below.
2. In the `showrunner-backend` repo: add `cues/[showId].json` (Adult and/or Jr) and add the show's pack to `manifest.json` (filenames → `r2Key`s).
3. Add the show's products to the product→packID mapping (now in **Supabase**, for Stripe) so purchases resolve to the right pack.
4. Add the new `[show]-adult`/`[show]-jr` showIds to the hardcoded `allowed` whitelist in `showrunner-backend/server.js`'s `/cues/:showId` route — easy to forget, causes a 404 even with everything else correct (bit Matilda on first attempt, 2026-07-06).
5. Push the backend repo → Render redeploys automatically. Done.

Full-show packIDs: `[show]-adult` / `[show]-jr`. À-la-carte packID = the video filename without `.mp4`.

**🔒 HARD RULE, no exceptions: every scene name — in `manifest.json`'s `files` keys, the actual `.mp4` filename, and every `packs` array reference — must be prefixed with its own show's name** (e.g. `Matilda_Birthday_Party`, never `Birthday_Party`). This is not a style convention to use best judgment on; it is a strict requirement enforced by an automated check (see below) that will fail the build/deploy if violated. Reason: `manifest.json`'s `files` object is **one single flat namespace shared across every show** — there's no per-show separation. Two shows with an identically-named scene will silently collide (whichever is added second overwrites the first in the manifest, and — worse — both would try to save to the *same local filename* on a customer's disk, since all shows share one `VIDEOS_DIR`).

- **History:** Matilda and Frozen originally both had a scene called `Title_Scene`; caught before it shipped, fixed by renaming Matilda's to `Matilda_Title_Scene`. At that time Shrek and Frozen were left with their pre-existing non-prefixed scene keys (36 in Frozen, 1 in Shrek — `Swamp_Wedding`), since both shows were already live with real customers and a rename would have forced a full video-library re-download for everyone.
- **Fully resolved 2026-07-11:** ahead of enabling à la carte purchasing for individual scenes across all shows, every remaining non-prefixed key in Shrek and Frozen was renamed (both the manifest key and the underlying `.mp4` filename), and every `packs` array reference updated to match. Confirmed zero outstanding/active licenses at the time, so no existing customer was affected. **All three shows (Shrek, Frozen, Matilda) are now fully prefixed — there is no more legacy exception.** Any new non-prefixed key from this point on is a bug, not a judgment call.
- **Automated enforcement:** `showrunner-backend/scripts/validate-manifest.js` exports a `validateManifest()` function that **`server.js` calls directly at the top of its own boot sequence**, before setting up Express — this is what actually guarantees enforcement, since it runs no matter how the process is launched. (An earlier version of this wired the check as an `npm` `prestart` hook instead; that turned out to do *nothing* on the real deployment, since Render's dashboard-configured start command runs `node server.js` directly rather than `npm start`, and `prestart` only fires through npm's own script lifecycle — caught and fixed 2026-07-11. The `npm run validate-manifest` CLI entry point is still there too, for a manual/local check, but the boot-time call inside `server.js` is the one that can't be silently bypassed.) It fails loudly and refuses to start if any `files` key doesn't start with its owning show's name (derived from the `packs` key, e.g. `matilda-adult` → expects `Matilda_` prefix — no hardcoded show list to maintain), if any `packs` entry references a key missing from `files` (dangling reference), or if the raw JSON text contains a duplicate key (which a normal JSON parse would otherwise silently swallow). `manifest.json` being broken is treated as a genuinely global problem (it's one shared file across every show) — this check is a hard whole-server boot gate.
- **Companion check, `validate-cues.js` (added 2026-07-13):** catches a related but different bug class — a manifest rename can update `manifest.json` without updating the `cues/*.json` files that reference those filenames by exact string, which silently breaks playback ("Video file not found" on every affected scene, despite a successful download) without breaking anything the manifest validator itself checks. Same boot-time-call pattern as `validate-manifest.js`. **Unlike manifest validation, this is NOT a whole-server gate** — cues files are independent per-show artifacts, so a bad reference in one show's cues only marks that show degraded (its `/cues/:showId` route returns a clean 503; `/health` lists it under `degradedShows`) while every other show keeps working and the server stays up. Caught for real 2026-07-13 via a live Frozen test purchase, after the naming-collision rename above updated `manifest.json` but missed 67 references across 4 cues files.
